## 1. Implementation Goal

Implement a first-class route-backed owner management surface that separates watch
intent from manage intent while keeping the library card action menu as the
compact per-item contextual entry:

- library cards keep primary playback navigation
- owner-manageable cards expose a visible action menu on desktop and mobile
- the card action menu contains `Edit` and `Delete`
- `Edit` navigates to `/videos/:videoId/edit`
- `/videos/:videoId/edit` renders a route-backed `Video details` management page
- metadata editing uses explicit `Save changes`
- visibility management is separate from metadata save
- delete uses the same confirmation behavior from the card menu and details page
- anonymous users and non-owners cannot discover or access owner-management controls

This is a flow redesign, not a hover-button hotfix.

## 2. Implementation Scope

### In Scope

- New owner-only route-backed video details surface at `/videos/:videoId/edit`.
- Server loader for the details page.
- Client details page UI and form behavior.
- Visible owner card action menu with `Edit` and `Delete`.
- Shared delete confirmation UI contract.
- Visibility section on the details page using the existing visibility API.
- Metadata save using the existing update API.
- Return-to-library search context preservation.
- Simple unsaved changes guard.
- Toast/snackbar acknowledgement for successful metadata save.
- Unit, UI, integration, E2E, and regression tests described by the test spec.

### Out Of Scope

- New visibility states.
- Upload workflow redesign.
- Playback authorization changes.
- Media encryption, manifest, segment, token, ClearKey, thumbnail, or storage
  path changes.
- Embedded player on the details page.
- Autosave, draft recovery, cross-tab conflict handling, or exact scroll
  restoration.
- Playlist actions, recommendations, reporting, social features, comments, likes,
  or sharing.
- New backend mutation APIs that duplicate existing update/delete/visibility
  route contracts.

- `app/routes/api.visibility.$id.ts`

These adapters call the library composition root:

- `app/composition/server/library.ts`

The composition root wires these application use cases:

- `UpdateLibraryVideoUseCase`
- `DeleteLibraryVideoUseCase`
- `ChangeLibraryVideoVisibilityUseCase`

The use cases already enforce owner/auth permission boundaries through:

- `VideoAccessPolicy`
- `findOwnedLibraryVideoById`
- `resolveVisibilityManagementTarget`
- non-disclosing `Video not found` behavior for unauthorized access where required

The implementation must not add a second metadata update, delete, or visibility
mutation path.

### 3.4 Existing Canonical Read Paths

Home currently loads catalog data through:

- `app/routes/_index.tsx`
- `app/composition/server/home-library-page.ts`
- `LoadLibraryCatalogSnapshotUseCase`
- `SqliteCanonicalVideoMetadataAdapter`

Single-video read support already exists at the port/infrastructure level:

- `LibraryVideoReadPort.findLibraryVideoById`
- `SqliteCanonicalVideoMetadataAdapter.findLibraryVideoById`

However, there is no dedicated application use case or page composition service
for owner video details yet. The new details loader should add a thin
application/composition path rather than filtering the entire home catalog in the
route or reading persistence directly from the route.

### 3.5 Existing Permission And DTO Mapping

Home DTO permission mapping is centralized in:

- `app/composition/server/home-library-video-dto.ts`

`toHomeLibraryVideoDto(video, viewer)` uses `VideoAccessPolicy.describePermissions`
and returns `HomeLibraryVideo.permissions`:

- `canEdit`
- `canDelete`
- `canManageVisibility`

The details page should reuse this DTO shape unless a narrower page DTO becomes
necessary. It must not infer edit/delete/visibility permissions from client-side
owner IDs.

### 3.7 Existing Navigation And Return Context

Home filter state lives in query parameters:

- `q`
- `tag`
- `notTag`
- `type`
- `genre`

Relevant files:

- `app/widgets/home-library/model/home-library-filters.ts`
- `app/routes/_index.tsx`
- `app/widgets/home-shell/ui/HomeShell.tsx`

`HomeShell` already has `mergeHomeSearchState` for preserving home search/filter
state in home navigation links. The edit link should preserve return context
without inventing a new global navigation store.

Recommended approach:

- `Edit` menu item links to `/videos/:videoId/edit?redirectTo=<encoded-home-path>`
- the return target is resolved through the existing safe redirect helper in
  `app/shared/lib/http/redirects.server.ts`, extended only if needed rather than
  duplicating open-redirect filtering logic
- the return target is accepted only when it resolves to a same-origin app path,
  with `/` as the safe fallback
- `Back to library` and post-delete navigation use the sanitized return target
- if no valid return target exists, fall back to `/`

### 3.8 Existing Route And Error Patterns

`app/routes/player.$id.tsx` is the closest route-backed media page example:

- resolves the viewer through `resolvePublicVideoAccess`
- delegates to a use case
- returns JSON loader data
- maps missing video to 404
- includes a route-level error boundary

The edit route is owner-management-only, but it must not use
`requireProtectedPageSession` because that helper redirects anonymous users to
login. Direct access by anonymous users, authenticated non-owners, missing videos,
and deleted videos must all return the same non-disclosing not-found style
response. The route should resolve an optional viewer through the existing
non-redirecting auth composition path, preferably
`resolveRequestViewer(request)`, and let the details use case normalize
anonymous, unauthorized, and missing targets.

## 6. Data And Control Flow

### 6.1 Library Watch Flow

1. Home loader returns `HomeLibraryVideo[]` with permissions.
2. `LibraryVideoCard` renders media/title as link to `/player/:videoId`.
3. User activates media/title.
4. React Router navigates to the existing player route.
5. Player route continues to use existing playback read access policy.

No implementation change should alter playback authorization or media request
behavior.

### 6.2 Library Edit Entry Flow

1. Home loader returns permission-capable video DTOs.
2. `LibraryVideoCard` determines whether any management action is allowed.
3. If at least one card-menu management action is available, the visible action
   trigger renders. In the current product policy this means `canEdit` or
   `canDelete`, because visibility-only library entry is not a supported product
   flow and visibility changes belong inside `Video details`. Mixed fake payloads
   are handled defensively by hiding unavailable menu items.
4. Menu opens on click/tap/keyboard.
5. `Edit` is rendered only when `canEdit` is true.
6. `Edit` links to `/videos/:videoId/edit?redirectTo=<encoded-current-home-url>`.
7. The details route loader independently enforces owner management access.

Client-side visibility of the menu is convenience only; server loader remains the
authority.

### 6.3 Details Loader Flow

1. Route reads `params.videoId`.
2. Route resolves an optional viewer without using a protected-page helper that
   redirects anonymous users to login.
3. Route converts the optional session to `VideoViewer`.
4. Route delegates to `loadOwnedVideoDetails`.
5. Use case loads a single video and vocabulary through the library module.
6. Missing, anonymous, and unauthorized direct access map to 404-style response.
7. Success serializes the DTO using `toHomeLibraryVideoDto`.

### 6.4 Metadata Save Flow

1. `VideoMetadataForm` owns form state through react-hook-form.
2. Submit sends only metadata fields to `/api/update/:id`.
3. The existing update route calls `UpdateLibraryVideoUseCase`.
4. Success returns the canonical updated `HomeLibraryVideo` DTO.
5. Details page updates local video state, resets dirty state, and shows a
   Sonner success toast.
6. Failure preserves edited values and renders an inline error near the form
   action area.

Metadata save must not send or mutate visibility.

### 6.5 Visibility Flow

1. `VideoVisibilitySection` renders current label-led visibility state.
2. `Make Private` calls `/api/visibility/:id` directly after click.
3. `Make Public` opens confirmation first.
4. The existing visibility route calls `ChangeLibraryVideoVisibilityUseCase`.
5. Success updates local video state and section feedback.
6. Failure keeps current local state and section error.

Visibility is deliberately separate from metadata save.

### 6.6 Delete Flow From Card

1. Card menu renders `Delete` only when `canDelete` is true.
2. `Delete` opens `DeleteVideoConfirmDialog` over the library page.
3. Confirm calls `/api/delete/:id`.
4. Success removes the video from current home state and closes the dialog.
5. Failure keeps the user on the library and shows dialog-level error.

### 6.7 Delete Flow From Details Page

1. Details page renders danger-zone delete only when `canDelete` is true.
2. Delete opens the same `DeleteVideoConfirmDialog`.
3. Confirm calls `/api/delete/:id`.
4. Success navigates to sanitized `redirectTo` or `/`.
5. Failure keeps the user on details and shows dialog-level error.

## 7. Architecture And Pattern Choices

### 7.1 Route-Backed Details Page

Use a file-system route instead of modal-only state because the page owns multiple
management concerns: metadata, visibility, delete, navigation, dirty-state, and
error handling. This matches the product spec and keeps browser navigation,
deep-linking, and permission denial testable.

### 7.2 Thin Routes, Application Use Cases

Routes should parse request/params, resolve sessions, call composition services,
and map response statuses. They should not implement library authorization or
database access directly.

This follows existing route patterns in `_index`, `player.$id`, and the current
write APIs.

### 7.3 Feature-Sliced UI

Reusable workflow UI should live under `app/features/*` when it represents a
video-management capability shared across pages:

- metadata form
- visibility section
- delete confirmation

The page/widget layer composes these features but does not own their internals.
The unsaved-changes guard is route/form navigation behavior rather than a
standalone product capability, so it should remain under
`app/widgets/video-details/model/useUnsavedChangesGuard.ts` while it is specific
to the details page. Only move it to a shared hook if another route needs the
same guard contract.

### 7.4 Existing API Reuse

The details page should call existing write APIs from client-side handlers rather
than adding route actions for the same mutations. This avoids duplicate write
contracts and keeps existing integration tests valuable.

### 7.5 Sonner Through shadcn

The repo has no existing toast primitive. Use shadcn Sonner instead of a custom
global toast implementation because:

- it is the documented shadcn toast path for React
- the project already uses shadcn primitives
- it keeps feedback implementation small and conventional
- it avoids custom accessibility/timing/state code for a non-core concern

## 8. Detailed Implementation Steps

### Step 1: Add Details Read Use Case

Add `load-owned-video-details.usecase.ts`.

Use dependencies:

- `LibraryVideoReadPort`
- `LibraryVideoSourcePort` or a smaller vocabulary port if introduced locally

Contract:

- empty `videoId` -> invalid input
- anonymous viewer -> not found
- missing video -> not found
- authenticated non-owner public video -> not found for edit route
- owner video -> returns video and vocabulary

Use `LibraryVideoReadPort.findLibraryVideoById` with the existing read scope, then
check owner-management access with `VideoAccessPolicy.evaluate({ operation:
'edit' })`. Do not make the route or read use case depend on mutation ports unless
implementation proves the read port cannot preserve the required non-disclosure
contract.

### Step 2: Wire Composition Service

Extend `app/composition/server/library.ts` with:

- `loadOwnedVideoDetails`

Use `SqliteCanonicalVideoMetadataAdapter` for read/vocabulary access. Avoid
instantiating SQLite adapters in the route.

### Step 3: Add Route Module

Create `app/routes/videos.$videoId.edit.tsx`.

Loader responsibilities:

- resolve an optional viewer without redirecting anonymous users to login
- convert the optional session to a `VideoViewer`
- call `getServerLibraryServices().loadOwnedVideoDetails.execute`
- serialize `createdAt`
- sanitize optional `redirectTo` through the existing safe redirect helper
- throw 404 for missing/unauthorized
- throw 400 only for structurally invalid requests if the use case requires it
- return no-store/private headers where session-sensitive

Component responsibilities:

- read loader data
- deserialize video date
- render `VideoDetailsPage`

### Step 4: Add Details Page And Widget

Create:

- `app/pages/video-details/ui/VideoDetailsPage.tsx`
- `app/widgets/video-details/ui/VideoDetailsView.tsx`

Layout contract:

- title: `Video details`
- top `Back to library`
- thumbnail/media context
- `Watch video` link
- metadata form
- separate visibility section
- separate danger zone
- desktop/wide tablet: two columns
- mobile: single column

Use stable responsive constraints and avoid nested card-in-card structure.

### Step 5: Generalize Metadata Form

Move or copy behavior from `EditHomeVideoForm` into
`VideoMetadataForm`.

Required changes:

- submit label becomes `Save changes`
- keep `Cancel`
- expose dirty-state changes to parent
- reset form values after successful canonical update
- render server save failure near action row
- keep zod/react-hook-form and existing field components

Do not add new metadata fields.

### Step 6: Add Unsaved Changes Guard

Create a small hook around React Router:

- `useBlocker`
- `useBeforeUnload`

Place it at `app/widgets/video-details/model/useUnsavedChangesGuard.ts` while it
remains specific to the details-page form.

Use it only when the metadata form is dirty and not currently saving.

Internal navigation:

- show a discard confirmation dialog
- `Stay` keeps route and values
- `Discard changes` proceeds with navigation

Browser unload:

- use native before-unload warning
- do not assert native dialog copy in tests

### Step 7: Extract Shared Delete Confirmation

Move delete confirmation behavior out of `HomeQuickViewDialog`.

Component props should include:

- `open`
- `videoTitle`
- `isDeleting`
- `error`
- `onCancel`
- `onConfirm`

The dialog must identify the target video, explain that deletion cannot be
undone, use a clear destructive label such as `Delete video`, and prevent
duplicate confirmation submissions while deletion is pending.

Use the same component from:

- card menu delete
- details page danger-zone delete

### Step 8: Extract Visibility Section

Move visibility behavior out of `HomeQuickViewDialog`.

The component should:

- render `Visibility: Private` or `Visibility: Public`
- render explanatory text
- render `Make Public` or `Make Private`
- confirm private-to-public
- call the existing visibility action client
- display section-local success/error feedback

### Step 9: Update Library Card Actions

Modify `LibraryVideoCard`.

Required behavior:

- visible action trigger when `canEdit` or `canDelete` is true
- the action trigger is visibly discoverable and opens without forced clicks,
  hover setup, or hidden focus traps
- the action trigger provides at least a 44 by 44 CSS px effective hit target,
  with non-overlapping spacing from adjacent controls
- action trigger remains keyboard reachable
- `Edit` menu item links to the details route when `canEdit` is true
- `Delete` menu item opens confirmation when `canDelete` is true
- `Delete` is placed last or visually separated in the menu and uses destructive
  treatment
- no `Quick view`, `Watch`, `Make Public`, or `Make Private` in card menu
- primary card link to player remains intact
- tag filter buttons still prevent navigation and filter correctly
- the `+N` tag overflow no longer opens Quick view; it uses non-management tag
  disclosure or inline expansion if hidden tag access is preserved in this pass

### Step 10: Update Home Widget State

Modify `HomeLibraryWidget` and `useHomeLibraryView`.

Required behavior:

- remove Quick view state from owner-management flow
- keep local filtered video list behavior
- card delete success removes the video from home state
- preserve search/filter query in edit return target
- use the existing safe redirect helper path for return navigation instead of
  adding a parallel URL sanitizer
- keep home filters and empty states working

### Step 11: Add Sonner

Use the project shadcn command:

```bash
bun run ui:add -- sonner
```

Then:

- mount `<Toaster />` in `app/root.tsx`
- use `toast.success(...)` after metadata save
- keep toast usage limited to non-critical success acknowledgement
- keep validation and server failures inline or section-local rather than
  toast-only

### Step 12: Remove Or Retire Quick View Management

After new flows pass tests, delete or reduce Quick view only if no remaining
product requirement needs it.

At minimum:

- management tests must no longer depend on Quick view
- owner card menu must not expose Quick view as the edit/delete path
- stale Quick view tests must be rewritten or removed

## 11. Risks And Mitigations

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Duplicate mutation path is introduced for details page | Policy drift and harder testing | Reuse `api.update`, `api.delete`, and `api.visibility`; keep new route read-only. |
| Details route leaks existence of private or non-owned videos | Security/privacy regression | Add use-case and route tests for anonymous, non-owner public, non-owner private, missing video. |
| Card action trigger remains visually hidden or too small on touch | Critical UX regression remains | Component and E2E/browser QA must prove visible trigger, no forced click, and at least a 44 by 44 CSS px effective hit target. |
| Metadata save accidentally changes visibility | Product contract violation | Form payload tests assert no visibility field; visibility section owns visibility calls. |
| Delete behavior drifts between card and details | Safety and copy inconsistencies | Use one shared delete confirmation component and one action client. |
| Unsaved guard becomes overcomplicated | User friction and brittle tests | Implement only simple dirty-state guard; no autosave, drafts, cross-tab, or exact scroll restoration. |
| Sonner conflicts with React Router SSR/hydration | Runtime UI issue | Add through shadcn generator, mount once in root layout, verify with typecheck/build/browser smoke. |
| E2E delete mutates shared fixture in a way that affects later tests | Flaky browser suite | Use disposable fixture or keep destructive delete primarily in UI/integration tests. |
| Quick view removal breaks tag overflow behavior | Regression in tag filtering | Replace `+N` with inline expansion or a non-management tag disclosure. Do not route it back to management Quick view. |
